## Undocumented capabilities found (new sub-feature ID candidates)

1. **No new SCHED-* capability found that isn't already covered by an existing (if inaccurately-described) sub-feature ID.** The task-scheduler subsystem itself (`t3/tasks/**`) appears architecturally stable and does not contain hidden functionality beyond what's already listed in the dictionary — if anything, several documented capabilities (history, notifications, retry/concurrency config, Pause/Resume, status state machine) do **not** exist in code and should be corrected to absent/partial rather than confirmed (see table above). This is the single most important finding of this pass: **the existing F-SCHED documentation significantly overstates operational maturity** (no execution history, no notifications, no retry/concurrency controls, no persistent run-status tracking, no pause/resume).
2. **"Save Aggregation to Remote 3T Lens Server" — a separate, unrelated feature that must NOT be folded into F-SCHED.** `t3/taskmanager/RemoteAggregationTask.java` (a simple Java `record`, not a `t3.tasks.Task` subclass) and `t3/taskmanager/LensApiClient.java` (POSTs an aggregation pipeline definition to `<remoteUrl>/task-api/tasks` with `config.type = "AGGREGATION"`, authenticated via OIDC device-flow tokens from `AccessManagerLicenseManager`) implement a one-shot, fire-and-forget "hand this pipeline to 3T Lens's own task API" action, exposed as a "Save on Remote Server" context-menu item in the Aggregation Editor (`AggregationComposite.addSaveToRemoteServerMenuItem()`), gated by `RemoteToolServerPicker.isRemoteTasksEnabled()`. Studio 3T Desktop does **not** manage, schedule, list, monitor, or receive results from these remote Lens-side tasks — it only submits the pipeline definition once. This is confirmed by commit `f5c3fc7b562` ("KONG-10915: Save Aggregation to Remote 3T Lens server") plus follow-ups `1cd4d0aab00`, `09f566c90de`, and OIDC device-flow fixes `78496c5c4ff`/`44f8a8355e2`/`59951b17abe`. Despite the `t3.taskmanager` package name and "Task" in the class name, this has zero code-level integration with the desktop Task Scheduler (`t3.tasks.TaskScheduleManager`/`Task.fromMap()` do not reference it, and aggregation is not a `TaskType`). **Recommendation**: this is not a candidate for a new `SCHED-*` ID at all — it belongs (if documented anywhere) under F-AGG (aggregation editor) cross-referenced to the separate 3T Lens product's own task API, not under Task Scheduler. Flagging explicitly so a future pass does not mistakenly document "remote/cloud aggregation scheduling" as a Task Scheduler capability — it would be inaccurate.
3. **Granular import task types** (see SCHED-task-types row above) — Collection Import, CSV Import, JSON Import, SQL Import, BSON-folder Import, and BSON-archive Import are each a distinct, independently schedulable `TaskType`, not sub-modes of one generic "Import" task. This is a documentation-precision correction rather than a new capability, but worth surfacing since a user building schedules sees 6 import options, not 1.
4. **No task-dependency chaining and no reusable task-template library beyond simple duplicate/save** were found — checked explicitly per the research brief. `Task.java` carries an explicit architecture comment: "In the current architecture, a task can have only one schedule. Having a second schedule will require a separate copy of the task." No "depend"/"chain"/"trigger" references exist anywhere in `t3/tasks`. Tasks are stored as individual `.task` zip files (XStream-serialized) under `<settings>/tasks/`, organized in a folder tree with manual ordering; `TaskFileManager.duplicateTask()` deep-copies a task and resets its schedule to null (a "clone as template" workflow exists implicitly via Duplicate, but there is no separate first-class "template" concept). This confirms these are **not implemented** (absent), not merely unverified — worth recording explicitly since they're common asks in this product category and the codebase gives a clean negative answer.
5. **exectools (`MongoDump`/`MongoRestore`/`MongoShell`) are general-purpose CLI wrappers, not scheduler-specific.** They are consumed by the broader import/export worker layer (`t3.utils.mongodb.importexport.*`, `t3.utils.export.MongoDumpUnit`), which BSON-related scheduled tasks reach indirectly (`TaskScheduleManager` → `task.execute(true)` → `AppWindow.runImport()`-equivalent → import/export worker → `exectools`). There is no scheduler-specific configuration layer on top of mongodump/mongorestore options — a scheduled BSON task uses exactly the same saved `ImportJob`/`ExportJob` unit configuration a manual run would use. No new sub-feature ID warranted here; recorded for completeness per the research brief's explicit ask about exectools.
